## Task 2993 — HTTP-429-Repro-Beleg

**Ziel:** Einen reproduzierbaren, "natürlichen" HTTP-429-Event als Telemetrie- und
Belegquelle erzeugen — kein synthetischer Fehlerobjekt-Bau, sondern ein echter
Loopback-HTTP-Server, der deterministisch mit 429 antwortet.

**Harness:** `system/tests/test_http429_telemetry_probe.py`
- `ThreadingHTTPServer` auf `127.0.0.1:0` in einem Daemon-Thread; Port wird vom OS
  vergeben, keine feste Portbindung, kein Konflikt mit Parallelläufen.
- `_RateLimitHandler` antwortet auf `POST /v1/chat/completions` deterministisch mit
  Status `429`, Header `Retry-After: 0` und JSON-Body
  `{"error": {"message": "rate limit exceeded"}}`.
- Fixture `rate_limit_server` liefert `http://127.0.0.1:<port>/v1`; `shutdown()`,
  `close()` und `join()` laufen im `finally` — kein Thread-Leak.
- Test `test_http429_event_contract_and_telemetry`: `HermesBackend(base_url, api_key="dummy",
  default_model="probe/429")`, dann `asyncio.run(backend.chat([...], retry_transient=False))`
  in `pytest.raises(BackendRequestFailure)`.
- Zusicherungen: `status_code == 429`, `kind == "http_error"`, `provider == "hermes"`
  (weil Hostname `127.0.0.1` nicht `openrouter.ai` ist), `retry_after_seconds == 0`
  (aus `Retry-After: 0` via `parse_retry_after`).
- Anschließend `telemetry.increment("model_calls", outcome="error", model="hermes") is True`
  als Beleg, dass der Event telemetrisch zählbar ist.

**Beleg:** `system/logs/evidence/http429_probe_2026-02-21.json` — dokumentiert Server,
Request, Response (Status, Header, Body), den normalisierten `event`-Block, den
Telemetrie-Aufruf und den Ausführungsstatus.
