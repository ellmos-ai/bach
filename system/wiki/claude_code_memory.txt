WAS IST DAS MEMORY-SYSTEM?
---------------------------
Claude Code hat zwei komplementaere Memory-Systeme, die beide bei jedem
Session-Start geladen werden:

  1. CLAUDE.md-Dateien: Instruktionen, die DU schreibst
     (Projekt-Struktur, Konventionen, Regeln)
  2. AUTO MEMORY: Notizen, die CLAUDE selbst schreibt
     (Learnings aus Korrekturen und Praeferenzen des Users)

Auto Memory ist seit 2026 ein offizielles, dokumentiertes Feature.
Claude entscheidet proaktiv, was sich zu merken lohnt (nicht jede
Session wird gespeichert). Statusmeldungen wie "Saved 2 memories"
zeigen aktive Speicherungen an.

VERZEICHNISSTRUKTUR (OFFIZIELLER STAND 2026-09)
-----------------------------------------------
  ~/.claude/projects/<project>/memory/
  ├── MEMORY.md           # INDEX: eine Zeile pro Memory, in JEDE Session geladen
  ├── user_role.md         # Topic-Datei (eine pro Memory-Thema)
  ├── feedback_testing.md  # weitere Topic-Dateien
  └── ...

WICHTIGE SCOPE-REGEL (GEAENDERT seit Feb 2026):
  - <project> wird aus dem GIT-REPOSITORY abgeleitet
  - Alle Worktrees UND Subdirectories des gleichen Repos teilen
    sich EINEN Auto-Memory-Ordner (Silo-Problem geloest!)
  - Ausserhalb eines Git-Repos: Projekt-Root wird verwendet
  - Auto Memory ist machine-local (kein Sync zwischen Maschinen)

VERZEICHNIS-ABLEITUNG
---------------------
  /Users/lukas/services/bach/.git  (Git-Root)
  -->  -Users-lukas-services-bach/memory/
  (auch wenn claude in .../bach/system/ gestartet wird!)

  Eigener Name moeglich: CLAUDE_CODE_PROJECT_DIR_NAME=<name>
  (erfordert Claude Code v2.1.234+)

WIE MEMORY FUNKTIONIERT
----------------------
1. MEMORY.md = INDEX:
   - Erste 200 Zeilen ODER 25 KB (je nachdem, was zuerst erreicht wird)
     werden bei jedem Gespraechsstart geladen
   - Alles darueber hinaus wird NICHT geladen (Truncation)
   - Claude Code mahnt bei Schreibvorgang nahe am Limit an:
     "eine Zeile pro Eintrag, Details in Topic-Dateien auslagern,
      veraltete Eintraege mergen/loeschen"

2. TOPIC-DATEIEN (z.B. feedback_sudo_notty_daemon.md):
   - Werden beim Start NICHT geladen
   - Claude liest sie on demand per Read-Tool, wenn noetig
   - Bei YAML-Frontmatter: Claude Code schreibt automatisch ein
     'modified'-Feld (ISO-8601) als Aktualitaetsmarker
     (erfordert v2.1.214+)

3. RETENTION-SCHUTZ:
   - Session-Transcripts werden nach cleanupPeriodDays geloescht
   - Memory-Dateien sind VON DIESES BEREINIGUNG AUSGENOMMEN
   - MEMORY.md und Topic-Dateien bleiben bis zur manuellen/
     Claude-gesteuerten Aenderung bestehen

4. SUBAGENTS:
   - Auto Memory der Haupt-Konversation wird NICHT in Subagents geladen
     (Ausnahme: fork erbt Parent-System-Prompt)
   - Subagents koennen EIGENE Auto Memory pflegen (subagent 'memory'-Feld)

EINSTELLUNGEN & STEUERUNG
------------------------
  ~/.claude/settings.json:
    "autoMemoryEnabled": true|false   # Auto Memory an/aus (Default: an)

  Umgebungsvariablen:
    CLAUDE_CODE_DISABLE_AUTO_MEMORY=1   # Auto Memory deaktivieren

  Custom-Speicherort:
    "autoMemoryDirectory": "~/mein-memory-dir"  in settings.json
    (absoluter Pfad oder ~/ - wird in allen Settings-Scopes gelesen)

  In-Session-Befehle:
    /memory   # Dateien browsen/editieren, Auto-Memory-Toggle,
              # Memory-Ordner oeffnen
    /context  # zeigt, welche Dateien in DIE Session geladen wurden

WAS MEMORY SPEICHERN SOLL
--------------------------
  JA (speichert Claude selbst):
    - Korrekturen und Praeferenzen des Users ("immer so machen...")
    - Stabile Patterns und Konventionen (mehrfach bestaetigt)
    - Loesungen fuer wiederkehrende Probleme

  NEIN (nicht speichern):
    - Session-spezifischer Kontext (aktuelle Task-Details)
    - Duplikate von CLAUDE.md-Inhalten
    - Spekulative Schlussfolgerungen

MEMORY vs. CLAUDE.md (OFFIZIELLE GEGENUEBERSTELLUNG)
-----------------------------------------------------
                          CLAUDE.md            Auto Memory
  Schreibt                Du                    Claude
  Inhalt                  Instruktionen/Regeln  Learnings/Patterns
  Scope                   Projekt, User, Org    Pro Git-Repository
                                                (Worktrees/Subdirs teilen)
  Laden                   Jede Session          Jede Session
                                                (200 Zeilen/25KB-Index)
  Groesse                 bis 4 MiB voll geladen 200 Zeilen/25KB-Index
                          (groessere: uebersprungen)  + Topic-Dateien on demand
  Zweck                   Verhalten lenken     Aus Korrekturen lernen

CLAUDE.MD-LADE-REIHENFOLGE (vom breitesten zum spezifischsten Scope):
  1. Managed Policy    /Library/Application Support/ClaudeCode/CLAUDE.md (macOS)
  2. User             ~/.claude/CLAUDE.md
  3. Projekt          ./CLAUDE.md oder ./.claude/CLAUDE.md
  4. Lokal            ./CLAUDE.local.md (in .gitignore!)
  Parent-Verzeichnisse: beim Launch. Unterverzeichnisse: on demand.
  NEU: .claude/rules/ fuer path-spezifische Regeln; AGENTS.md wird
  ebenfalls unterstuetzt. /init (CLAUDE_CODE_NEW_INIT=1) generiert
  CLAUDE.md interaktiv (Skills, Hooks, Regeln mit vorschlagen).

BEKANNTE EIGENHEITEN
---------------------
  - Gleicher Git-Repo-Root = gleiche Memory (auch verschiedene
    Arbeitsverzeichnisse/Worktrees im Repo)
  - Memory wird NUR geladen, wenn claude im passenden Kontext startet
  - Legacy: Aeltere Claude-Code-Versionen leiteten <project> aus dem
    Arbeitsverzeichnis ab; dadurch existieren historische Projektordner
    parallel (siehe lokale Beobachtung)
  - /memory zeigt auch NICHT existierende CLAUDE.md-Eintraege an
    (Anlegung per Auswahl moeglich)

BACH-KONTEXT
------------
Fuer BACH ist das Memory-System besonders relevant:
  - ALT (Feb 2026, Windows): ~42 isolierte Projekt-Memories,
    Wissen-Silos zwischen BACH-Dev, Forschung, MCP etc.
  - NEU (Sep 2026, Mac): BACH ist EIN Git-Repo --> alle BACH-Starts
    teilen sich EINEN Memory-Ordner. Die Silo-Problematik ist durch
    die Git-Root-Ableitung vom System geloest.
  - Home-Memory (~ohne Git-Repo) bleibt separat (Projekt-Root-Ableitung)
  - Fuer einheitliches Memory ueber mehrere Repos: CLAUDE_CODE_PROJECT_DIR_NAME
    oder autoMemoryDirectory verwenden (alle Starts in einen Ordner lenken)
