REGLAS DE WORKER: CONFIGURACIÓN Y VISUALIZACIÓN DE LEASE
========================================================

REQUISITO PREVIO
El contrato común de Task-Master taskplan.worker_policy debe estar instalado:
worker-review-policy.v1alpha1. Si falta o su versión es desconocida, las
reglas de worker no están disponibles. No hay ningún segundo fallback de
política de BACH.

Instalar explícitamente el paquete opcional desde la raíz de BACH:
python -m pip install -e ".[worker-policy]"

El extra fija el núcleo común al commit verificado de Task-Master
5924b71b2a93e59e625b5c9afaa6e84966bf49d3. El número de versión general
taskplan==0.7.0 por sí solo no identifica este estado. Esta vía de instalación
está separada del antiguo setup.py --extras. Tras la instalación, leer status
de forma independiente. Una instalación no inicia ningún worker ni sustituye
ninguna aceptación del usuario.

ACCESO MEDIANTE CLI Y BIBLIOTECA
bach worker-policy status
bach worker-policy task_show 41

from bach_api import worker_policy
ok, text = worker_policy.raw("status")
ok, text = worker_policy.raw("task_show", 41)

set acepta un objeto JSON con configuration_version, policy y selection.
task_set acepta el ID de tarea y JSON con task_id, task_version,
configuration_version y override. Ejemplo sin acción de escritura:

import json
ok, text = worker_policy.raw("status")
snapshot = json.loads(text) if ok else None

Leer siempre de nuevo los valores de versión; en caso de conflicto, recargar
y conciliar los cambios de forma consciente. Una mutación rechazada no se
repite automáticamente.

GUI-API
GET/PUT /api/system/worker-policy
GET/PUT /api/tasks/{id}/worker-policy

Los cuatro accesos requieren un dispositivo registrado activo. Los tokens
pertenecen a la cabecera Authorization existente o a la cookie del dispositivo,
no a las URL. Un uso local/nativo de la biblioteca utiliza el mismo servicio
de configuración.

REGLAS Y ALMACENAMIENTO
La política global y las anulaciones vinculadas a tareas residen en el
almacén system_config existente de la base de datos canónica de BACH. La
revisión y CAS están separados del contenido y estado de la tarea. Reset
aumenta la revisión de configuración; incluso volver a los mismos valores
invalida estados de escritura antiguos. Las lecturas no modifican ni el
esquema ni la configuración. Un almacenamiento ausente no equivale a un valor
predeterminado vacío válido.

mode=null hereda el modo. Las anulaciones booleanas distinguen null, false y
true. Una obligación de revisión de usuario establecida no puede eliminarse
mediante false ni Reset. Las reglas guardadas no otorgan autorización de
revisión.

Una confirmación de guardado no inicia ningún worker ni acepta ningún
resultado. La vista de tarea informa explícitamente not_evaluated sin una
integridad de resultado verificada. El servicio de resultados, la selección y
la ejecución real deben aplicar las reglas por separado. Esta proyección de
configuración no es ninguna aceptación productiva ni de usuario.

VISUALIZACIÓN DE LEASE
Las rutas de estado existentes de Worker/Core-Agent pueden proyectar un lease
de tarea activo a partir de la vinculación confirmada del controlador y la
vinculación canónica de tarea. Generación, versión de tarea, titular, fence,
heartbeat y expiración deben coincidir. Un ID de tarea guardado o el estado
del perfil por sí solos no demuestran un lease activo.

lease_id en esta proyección de estado es una referencia pública de observación
sha256:<digest>, marcada mediante lease_id_kind=observation_sha256 y
source=native_task_db. El Claim-ID privado permanece en el cliente de lease.
La referencia de observación no otorga ningún derecho de Claim, Renew o
Release.

La cuenta atrás y la ordenación son presentaciones opcionales. No modifican ni
el lease de tarea ni el presupuesto de turnos, no prolongan el tiempo de
ejecución y no inician ningún trabajo.
