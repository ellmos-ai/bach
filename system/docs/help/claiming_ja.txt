=== モデル & RAM クレーム (RAM-DISTRIBUTOR & モデルランタイム) ===

概要:
  BACH および Ocean には固定のモデルスロットはなくなりました。すべてのエージェン
  ト ("あなたのエージェント") は、プライマリモデル + フォールバックチェーンに直
  接バインドされています。実行時には 2 段階のクレームが行われます:
    1. RAM クレーム (メイントーチ / RAMDistributor): 誰が物理 RAM/VRAM を占有
       できるか (ローカル 27B モデル vs. コンピュートパイプライン)?
    2. モデルランタイムクレーム (モデルトーチ / HostInferenceGate): ロード済みモ
       デル上の次の推論ターンを 4 つのユーザー近接度クラスに基づいて誰が取得する
       か?

ユーザー近接度による 4 つの優先度クラス (UserProximity):
  クラス 1 (DIRECT_INTERACTIVE)    : ユーザーが直接待機中 (Chat, Talk)
  クラス 2 (DELEGATED_FOREGROUND)  : ユーザー/Chat が明示的に委託したエキスパート
  クラス 3 (SCHEDULED_ROUTINE)     : 期限到来のスケジュールまたはルーチンエージェント
  クラス 4 (AUTONOMOUS_BACKGROUND) : バックグラウンドワーカー (Buddha Always-On)

ケース A: 別プロセスが RAM / VRAM を必要とする場合 (コンピュート / 独自モデル)
  1. システムトレイ (ellmos-tray) または GUI (/agenten/running) で:
     "🔥 RAM-Distributor & Modell-Claim" ->
     "🔓 Modell & RAM jetzt für andere Prozesse freigeben"
  2. HTTP-API / CLI 経由:
     curl -X POST http://127.0.0.1:8081/api/fackel -H "Content-Type: application/json" -d '{"preference":"compute"}'
     curl -X POST http://127.0.0.1:11434/api/generate -d '{"model":"qwen3.8:27b-mlx","keep_alive":0}'
  3. コンピュートロック経由 (~/.memwatchdog/compute_active.lock):
     {"active_compute_jobs": [{"pid": <PID>, "name": "<job>"}]} を記入します。

ケース B: 別プロセスがローカルモデルをクレーム / 使用したい場合
  1. Python で HostInferenceGate を介して協調的に (バックグラウンドワーカーを退避):
     from hub._services.chat.host_inference_gate import HostInferenceGate
     async with HostInferenceGate().turn("mein-prozess", "foreground"):
         ...
  2. BACH Control API (:8081/api/chat) 経由で直接:
     curl -X POST http://127.0.0.1:8081/api/chat -H "Content-Type: application/json" \
       -d '{"prompt": "...", "chat_id": "mein-prozess"}'
  3. モデルバインディングの確認と管理:
     bach model-sockets list --json
     bach model-sockets catalog --json
