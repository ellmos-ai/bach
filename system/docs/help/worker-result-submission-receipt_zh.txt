Worker 结果提交证明
=============

#2210 的此组件补充了现有的结果服务。它记录了在何种任务版本、Worker 代际和
Fence 下提交了何种结果，以及当时保存了何种 Worker 策略。任务、结果和修正的管
理仍保留在以往的 BACH 存储中。

证明内容
----

租约服务在其写入事务下检查有效的工作租约。结果、向 review 的状态变更、租约
释放以及历史证明属于同一事务。事后证明不再要求依然有效的 Claim-ID：租约在提
交时已被有意识地归还。更高的 Fence、变更的委托或新的修正轮次会使旧的当前结
果状态失效。

该证明将任务和结果与代际、Fence、任务版本、结果摘要、历史持有者名称、提交时
间、状态事件和释放事件关联起来。持有者名称来自租约请求。它既不确认模型身份，
也不授予审查者权限。

提交时可用的全局策略和任务覆盖会连同配置版本一起记录下来。之后的设置更改不会
重写此历史配置。如果缺少可选的公共策略契约或配置存储，这在证明中会明确显示为
不可用。结果提交仍然可行。

与任务完成的界限
--------

提交证明确认已保存的提交及其历史记录。要实现专业完成，仍然缺少针对范围和项目
状态、工作树指纹、当前锁、契约履行、经过身份验证的独立模型审查以及必要时
GitHub 验收的独立来源。仅凭 PR 地址不能确认当前的 Head、已通过的检查或批
准。

已保存的策略尚不是已应用的策略决策。此组件不会产生自动 done，也不替代强制性
的用户验收。现有的 Submit-Payload 仍然仅包含 generation 和 result；Worker
不能设置自己的完整性标志。已确认的释放保持为 accepted=false 的 review 状态。

兼容性与运行
------

较旧的结果行仍可作为 Legacy 读取。新提交带有自己的版本标识；缺少证明字段不会
使其成为旧数据。它们不会获得事后编造的完整提交证明。新证明会根据规范结果行和
相关历史事件进行检查。损坏或错误分配的证明不得允许当前的结果验收。

架构扩展在现有的用于提交和修正的显式架构写入路径中进行。结果 GET 既不修改架
构也不修改数据。本文档不执行也不批准生产安装或迁移。

回读与进一步集成
--------

GET /api/tasks/{id}/result 在 result.submission 下返回提交证明的可用性：
available、unavailable 或 legacy_release_only。哈希 submission_revision 绑
定历史提交证明。它尚不是公共完成契约的完整 result_revision；为此还缺少前述
的范围、项目和工作状态证明。

冻结策略的可用性单独列在 result.submission.policy.availability 下。在此组件
中，不可用的可选策略元数据既不阻止有效提交，也不阻止以往的个人验收和修正路
径。相反，损坏的提交证明会阻止验收。关于进一步的自动完成行为，此处尚未保存或
执行任何策略决策。
