TASKS - Aufgaben-System
=======================

STAND: 2026-05-17

Das Task-System (Schicht 5) orchestriert die Arbeit zwischen User und
Partner-Agenten (Claude, Gemini, etc.).

KERNKONZEPTE
------------
- MANUELLE TASKS: Via `bach task add` (Tabelle: `tasks`).
- GESCANNTE TASKS: Aus Code-Kommentaren (Tabelle: `ati_tasks`).
- MULTI-PARTNER: Zuweisung via `--assigned` an Agenten oder User.
- FÄLLIGKEIT: Optionales `due_date` als gültiges ISO-Datum `YYYY-MM-DD`.
- DISTI-TIERS: Tasks sind via `dist_type` (User/Template/Core) getrennt.

ZWEI ZUGRIFFSWEGE (NEU ab v2.0)
-------------------------------
BACH hat ZWEI parallele Zugangswege - beide nutzen dieselben Handler + DB:

1. CLI (für Menschen am Terminal):
     python bach.py task add "Titel" --priority P4

2. LIBRARY-API (BEVORZUGT für LLM/Scripts):
     from bach_api import task
     task.add("Titel", "--priority", "P4")
     task.list()
     task.done(42, "--note", "Erledigt")

CLI-BEFEHLE (bach task)
-----------------------
  add <titel>       Erstellt Task (--priority P1-P4, --description, --category,
                    --due YYYY-MM-DD)
  list [status]     Gefilterte Übersicht (pending/open/in_progress/done/blocked/all)
  list --filter     Nach Begriff im Titel filtern
  list --assigned   Tasks für einen bestimmten Partner
  list --unassigned Tasks ohne Zuweisung
  show <ID>         Details inkl. Beschreibung und Historie
  edit <ID>         Bearbeitet Task (--title, --description, --category, --assigned,
                    --required-model MODEL, --assigned-slot SLOT)
  done <ID>         Markiert Task als erledigt (Multi-ID, --note)
  block <ID>        Blockiert Task(s) (Multi-ID, --reason)
  unblock <ID>      Entblockt Task(s) (Multi-ID)
  reopen <ID>       Öffnet erledigte Task(s) erneut (Multi-ID)
  delete <ID>       Löscht Task(s) permanent (Multi-ID)
  priority <ID> <P> Ändert Priorität (P1-P4)
  result-service-history <ID> --service-id SERVICE-ID [--limit N] [--before EVENT-ID]
                    Ergebnisverlauf mit enger Service-Anmeldung lesen
  result-service-correct <ID> --service-id SERVICE-ID [--note TEXT]
                    Genau das angezeigte Review-Ergebnis zur Korrektur zurückgeben
  result-service-accept <ID> --service-id SERVICE-ID
                    Genau das angezeigte Review-Ergebnis separat annehmen
  assign <ID>       Zuweisung an Partner (--to GEMINI/COPILOT/etc.)
  depends <ID>      Zeigt Abhängigkeiten an
    --on <X>        Fügt Abhängigkeit hinzu (Task wartet auf X)
    --remove <X>    Entfernt Abhängigkeit
    --clear         Löscht alle Abhängigkeiten

LIBRARY-API BEISPIELE
---------------------
  from bach_api import task

  # Task erstellen
  task.add(
      "Doku schreiben",
      priority="P2",
      category="docs",
      due_date="2026-09-15",
  )

  # Tasks auflisten
  task.list("pending")
  task.list("open")         # Legacy-Status
  task.list("in_progress")  # Aktuell in Bearbeitung
  task.list("all", "--assigned", "GEMINI")
  task.list("--unassigned")

  # Titel und weitere CLI-Felder über den gemeinsamen Handler bearbeiten
  task.raw("edit", "42", "--title", "Neuer Titel")

  # Keyword-only API für Worker-Routingfelder
  task.edit(42, required_model="<Modell-ID>", assigned_slot="<Worker-ID>")
  task.done(100, 101, 102, "--note", "Alle erledigt")
  task.assign(200, "--to", "COPILOT")

  # Abhängigkeiten
  task.depends(306, "--on", "305")  # Task 306 wartet auf 305
  task.depends(306)                 # Abhängigkeiten anzeigen


Ergebnis-Service-Befehle lesen die Service-Anmeldung verdeckt per getpass. Der
Service besitzt nur die ausdrücklich gespeicherten Task-/Kategorie- und
Aktionsrechte. Korrektur und Annahme benötigen zusätzlich die Leseberechtigung,
damit die CLI den Ergebnis-Hash und die aktuelle CAS-Version anzeigen kann.
Vor beiden Schreibaktionen bindet eine Bestätigung Task-ID, Ergebnis-ID und
SHA-256; die Anmeldung wird weder ausgegeben noch gespeichert. Die vier Rechte
read, history, correction und accept sind voneinander getrennt.

KOORDINATION UND WORKER-ROUTING
------------------------------
  # Den eigenen Lease-Anspruch mit der erhaltenen Lease-ID prüfen
  task.lease_read(42, lease_id="<eigene Lease-ID>")

Ohne übergebene Lease-ID beweist own=false keinen Hostkonflikt. Eine
Zuweisung allein ist keine Lease; produktive Arbeit benötigt einen gültigen
Anspruch mit Fence und aktueller Taskversion. assigned_slot ist in diesen
Task-APIs ein internes Legacy-Routingfeld. Cloud- und Free-Worker benötigen
keinen lokalen Modellslot. Lokale Modellressourcen werden separat geregelt.
Priorität wird über priority <ID> <P1-P4> geändert, nicht über edit.

SCAN-TASKS (hub/ati.py)
-----------------------
  bach ati onboard --check    Scannt das Filesystem nach neuen Aufgaben.
  bach scan tasks             Listet Aufgaben aus `ati_tasks` auf.

DATENBANK (Schicht 1)
---------------------
- `tasks`: id, title, description, status, priority, assigned_to, delegated_to,
  depends_on, category, tags, due_date, created_at, completed_at, updated_at,
  dist_type. `due_date` ist `NULL` oder ein ISO-Datum `YYYY-MM-DD`.
- `ati_tasks`: Gescannte Aufgaben mit Source-Link (File/Line).
- DB-Pfad: BACH_DB

ERGEBNIS-REVIEW MIT SEPARATER SERVICE-IDENTITÄT
------------------------------------------------
Die Service-Credential wird verdeckt abgefragt. Die CLI zeigt sie nicht an und
speichert sie nicht. Sie ist kein allgemeines Geräte-/API-Token; diese Befehle
legen keine Credentials an. Jeder Zugriff braucht einen eigenen Scope für eine
ausdrückliche Task-ID oder Kategorie. Leserecht, Verlauf, Korrektur und Annahme
sind getrennt; ein Recht gewährt kein anderes. Die CLI fragt das Service-
Credential verdeckt ab und übergibt es nie als Befehlsargument.

  result-service-history <ID> --service-id SERVICE-ID [--limit 1-50] [--before EVENT-ID]
    Liest nur den autorisierten Verlauf und ändert keinen Taskstatus. Erfordert
    den Scope history.
  result-service-correct <ID> --service-id SERVICE-ID [--note TEXT]
    Fordert eine Korrektur für das aktuelle Review-Ergebnis an. Erfordert read
    und correction. Die CLI zeigt Ergebnis-ID und SHA-256 und fragt vor dem
    Senden der aktuellen Task-/Ergebnis-/CAS-Werte nach Bestätigung.
    Der Hinweis umfasst 1 bis 1200 Zeichen.
  result-service-accept <ID> --service-id SERVICE-ID
    Nimmt das aktuelle Review-Ergebnis an. Erfordert read und accept. Die CLI
    zeigt Ergebnis-ID und SHA-256 und fragt vor dem Senden der exakten
    Task-/Ergebnis-/CAS-Werte nach Bestätigung.

Fehlender Scope, fehlende Produzentenbindung, Schema oder Richtlinie führen zu
Ablehnung bzw. „nicht verfügbar“; es gibt keinen breiten Token- oder Legacy-
Fallback.
