モデルによる独立した結果レビュー
===============

提出されたワーカー結果は、最初はステータス review に留まります。モデルレビュー
は同じタスクデータベースとキュー内の追加タスクです。適合する通常のタスクが先に
引き受けられます。追加のスケジューラや自動モデルプロビジョニングはありません。

前提条件
----
ローカルコントローラには、確認済みの HTTP バックエンドルート、実際のモデルリター
ン、有効な結果提出、および現在の Git 作業コピー証明が必要です。別途権限を与え
られた人物がモデルエイリアスをモデルアイデンティティに割り当て、既存のワーカー
設定で許可されるレビュアーとレベルを決定します。一般的なデバイス登録だけではこ
れらの権限には不十分です。変更は既存の設定バージョンを使用し、並列変更時には拒
否されます。

計画されたモデル名やスロットラベルはアイデンティティを証明しません。実際のルー
トと呼び出し中に有効なエイリアス割り当てが実行証明に記録されます。古い証明に後
からモデルアイデンティティが付与されることはありません。欠落または変更された証
明では独立したレビューは許可されません。API キーはプロセス内に留まり、これらの
証明にテキストとしてもキーハッシュとしても表示されません。

フロー
---
有効な提出の後、レビュー引き受けが有効になっている場合、具体的な完全な結果リビ
ジョンに対して厳密に 1 つのレビュータスクが作成されます。対象タスクは review の
ままです。レビュータスクは対象タスクの Done に依存しません。コントローラは、別
のモデルアイデンティティ、別のスロット、および別の実行世代に対してプライベート
で譲渡不可能な Grant を発行します。公開または外部のクレームはそれによって追加の
権限を取得しません。

レビューは既存のモデル、リソース、リース、および停止チェックを通過します。対象
の依頼と結果を読み取ることができ、自身のレビュー結果のみを提出できます。コント
ローラは実際の最後のモデルリターンを厳密にこの Submit 呼び出しにバインドします。
アイデンティティや独立性に関するモデルの記述は権限として採用されません。

構造化された判定には status (approved、findings、または rejected)、summary、お
よび task_contract_met が含まれます。approved には task_contract_met=true が必
要です。欠落しているレビュー証明は所見として可視のままにする必要があります。記
録されたレビューは実行されたレビュータスクのみを完了します。元のタスクは review
のまま残り、個人的に受け入れるか修正のために差し戻すことができます。個人承認は
このレビューによって代替されません。

最新性と制限
------
読み取りビューは、現在の完全な Git/結果リビジョンを再比較した後にのみ記録済みレ
ビューを確認します。依頼、結果、ルート、モデル割り当て、ポリシー、または作業コ
ピーの変更は、未検証の再利用を防止します。レビュータスクはさらなるレビュータス
クを生成しません。読み取り呼び出しはテーブルを作成せず、モデルも起動しません。

このコンポーネントは 2 回目のモデル呼び出しを追跡可能なレビュー証明と結び付けま
す。すべてのユーザー、GitHub、契約、および修正ルールを含む完全な自動完了決定
は、依然として独立した未完了の統合ステップです。ソース変更だけではネイティブイ
ンストールは有効になりません。
