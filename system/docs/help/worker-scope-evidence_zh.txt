WORKER-SCOPE-EVIDENCE — 结果的项目与工作树证明
==============================

已提交的结果可以获得不可变的范围（Scope）证明。第一个适配器使用位于
bach-task/<Task-ID> 的干净 BACH 任务工作树的现有注册。其他项目需要各自连接
到其实际的仓库/范围权威机构。缺少证明不妨碍以往的个人验收或修正。

私有控制器记录规范 Result、其任务版本、代际、Fence 和提交修订版本，以及仓
库、分支、Head 和 Git 树。解析后的本地路径仅以 SHA-256 形式保存。现有的公
开源码锁定会被检查；其缺失不会被输出为公开确认的来源。提示词、响应、私有租约
ID 和凭据不属于此证明。

定义的 Git 范围涵盖暂存区（Index）、已跟踪文件和未忽略的新文件。staged/
unstaged/untracked 更改以及 assume-unchanged 和 skip-worktree 会阻止正向
证明。子模块和已配置的 Git 文件过滤器在第一个适配器中保持不可用；此范围检查
不会执行过滤程序。已忽略的文件明确位于此 Git 范围之外。干净的提交不能证明委
托在专业上的履行。

Git 和 SQLite 没有共同的事务。Git 和当前锁在 SQLite 写入锁之外记录；在写入
锁内部会重新检查规范结果绑定。该证明描述的是观测到的状态。它不能证明两次查询
之间的永久排他性或不可变性。

read_result() 在 SQLite 读取快照内仅检查已保存的证明和历史记录。
result.scope.availability=recorded 表示：历史证明有效，当前工作树尚未重新
确认。此时 result.result_revision 保持为 null。本地 SDK 获取和 API-GET 随
后会重新检查 Git/注册/锁。API 会在关闭连接后在其事件循环之外执行此检查。由
调用方已打开的 SQLite 快照不会被 SDK 关闭；在此快照内不会执行额外的 Git 投
影。

只有在确认范围未发生变化时才会显示 availability=available。变更的 Head、脏
工作树或不可用的 Git/锁服务会返回 unavailable 且不返回完整的结果修订版本。
现有的结果证明绝不会被更新的工作树状态覆盖。新的提交需要新的结果代际。

完整的 result_revision 绑定了提交修订版本、实际确认的执行修订版本以及范围
证明摘要/历史事件。缺少执行证明时它保持为 null。在 CLI 运行中，范围在 Submit
之后可能已经存在；尽管如此，修订版本仍然仅在实际模型返回和已确认的执行关联之
后才会产生。丢失的 Submit-ACK 只能通过精确规范地回读自身预期的私有提交来重
建。

私有本地捕获使用 TaskLeaseClient._capture_task_scope 和
WorkerLeaseBinding.capture_confirmed_scope。分发器在确认任务操作后于绑定锁
之外调用它们。直接的本地调用方可以显式调用它们；result_state 会在需要时首
先重建实际的 Submit。在 Binding 中会避免对同一结果 ID 的重复成功捕获。当前
的公共获取继续重新检查其范围。远程客户端既不会收到自述端点，也不会收到本地
DB 回退。

有效的修订版本既不授予审查权限，也不授予 Done。作者和审查者身份、模型级别、
独立性、专业任务契约、用户义务和 GitHub 门控必须提供各自经授权的证明。之后的
批准必须重新检查届时的当前状态。
