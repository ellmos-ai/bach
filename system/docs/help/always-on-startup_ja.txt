# ネイティブ Always-On 再開

Control-API は設定されたポートのバインドに成功した後、独自の起動チェックを開始
します。正規のリード上で保存済みスロット buddha_always_on のみが対象となります。
他のスロットや動的ワーカーには自動起動は行われません。

このチェックはデフォルト値をユーザー承認や Creator 権限として引き継ぎません。
Enabled は明示的に true である必要があります。手動で一時停止 (paused)、停止、
無効化、期限切れ、完了された状態は保持されます。この固定ワーカーの通常停止は今後
paused を保存します。明示的に要求された目標状態は有効なまま維持されます。以前の
自動クールダウン一時停止は継続可能であり、起動チェックは許可前に既存のカウントダ
ウンを待機します。読み取り不能な一時停止開始時刻では起動が許可されません。

Ollama および LM Studio は、実際のローカルモデルチェック後にのみ考慮されます。
クラウドプロバイダおよび :cloud モデルは除外されます。ループバックエンドポイン
トだけではローカルモデルの証明になりません。ローカルモデルサーバーがまだ準備でき
ていない場合、起動チェックは 30 秒待機して現在の設定を再読み込みします。チェック
は許可の確認または既存のネイティブ許可によって終了し、サーバーのシャットダウン時
に停止します。その中止シグナルは予約済みの自身の世代にアトミックに結び付けられて
います。これにより、シャットダウン時にまだ待機中のロール許可が後からワーカーを起
動することはできず、後の別世代には停止が送られません。

ローカルモデルチェックと起動は共通の未変更の設定バージョンを使用します。既存のネ
イティブ許可は、このバージョン、現在の Control インスタンス、および保存済みの
Enabled 状態を再確認します。並列の試行ではコントローラごとに最大 1 世代のみが予
約されます。未確認の物理起動は CAS 競合として再試行されません。

通常のタスクリース、コンテンツバージョン、600 秒の Creator 猶予期間、トーチ、
およびローカル推論制御はそのまま使用されます。実際に確認されたタスク引き受けのみ
がモデルラウンドを許可します。空のキューは許可された継続ワーカーを利用可能な状態
に保ちます。クラッシュ後の自身の再開では、確認済みリースを迂回することなく
held、Creator、およびコンテンツの競合を待機します。正規に終了状態の古いタスク状
態は、未変更のタスクポインタの条件付き削除のみを許可します。それが自身の完了済み
タスクや自身の結果として出力されることはありません。その間に再割り当てされたタス
クポインタは保持されます。

## 受け入れ

本文書はソース契約を記述したものです。本番受け入れには、新しい Control プロセス、
新しいサービスインスタンス、厳密に 1 つの物理 Always-On 世代、および確認済み
結果を持つ実際のリースタスクが必要です。単なるソース更新やテストの一部の成功では
この受け入れを証明できません。クラウドワーカーは Control 再起動後も引き続き自動
再起動されません。
