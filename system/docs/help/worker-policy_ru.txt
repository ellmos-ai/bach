ПРАВИЛА ВОРКЕРА: КОНФИГУРАЦИЯ И ОТОБРАЖЕНИЕ LEASE
=================================================

ПРЕДПОСЫЛКА
Общий контракт Task-Master taskplan.worker_policy должен быть установлен:
worker-review-policy.v1alpha1. Если он отсутствует или его версия
неизвестна, правила воркера недоступны. Второго fallback-механизма политики
BACH не существует.

Явно установить опциональный пакет из корня BACH:
python -m pip install -e ".[worker-policy]"

Этот extra фиксирует общее ядро на проверенном коммите Task-Master
5924b71b2a93e59e625b5c9afaa6e84966bf49d3. Один лишь общий номер версии
taskplan==0.7.0 не идентифицирует это состояние. Этот путь установки
отделён от старого setup.py --extras. После установки независимо прочитать
status. Установка не запускает воркера и не заменяет пользовательскую
приёмку.

ВХОД ЧЕРЕЗ CLI И БИБЛИОТЕКУ
bach worker-policy status
bach worker-policy task_show 41

from bach_api import worker_policy
ok, text = worker_policy.raw("status")
ok, text = worker_policy.raw("task_show", 41)

set принимает JSON-объект с configuration_version, policy и selection.
task_set принимает ID задачи и JSON с task_id, task_version,
configuration_version и override. Пример без действия записи:

import json
ok, text = worker_policy.raw("status")
snapshot = json.loads(text) if ok else None

Значения версий всегда читать заново; при конфликте перезагрузить и
осознанно сверить изменения. Отклонённая мутация автоматически не
повторяется.

GUI-API
GET/PUT /api/system/worker-policy
GET/PUT /api/tasks/{id}/worker-policy

Все четыре обращения требуют активного зарегистрированного устройства.
Токены должны находиться в существующем заголовке Authorization или cookie
устройства, а не в URL. Локальное/нативное использование библиотеки
использует тот же сервис конфигурации.

ПРАВИЛА И ХРАНЕНИЕ
Глобальная политика и привязанные к задачам переопределения находятся в
существующем хранилище system_config канонической базы данных BACH. Ревизия
и CAS отделены от содержимого и статуса задачи. Сброс (Reset) увеличивает
ревизию конфигурации; даже возврат к прежним значениям делает старые
состояния записи недействительными. Чтение не изменяет ни схему, ни
конфигурацию. Отсутствующее хранилище не равнозначно пустому
действительному значению по умолчанию.

mode=null наследует режим. Булевы переопределения различают null, false и
true. Установленная обязанность пользовательской проверки не может быть
удалена через false или Reset. Сохранённые правила не дают права на
рецензирование.

Подтверждение сохранения не запускает воркера и не принимает результат.
Представление задачи без проверенной целостности результата явно сообщает
not_evaluated. Сервис результатов, выбор и фактическое выполнение должны
применять правила отдельно. Эта проекция конфигурации не является
продуктивной или пользовательской приёмкой.

ОТОБРАЖЕНИЕ LEASE
Существующие пути статуса Worker/Core-Agent могут проецировать активный
lease задачи из подтверждённой привязки контроллера и канонической привязки
задачи. Поколение, версия задачи, держатель, fence, heartbeat и срок
действия должны совпадать. Одного сохранённого ID задачи или статуса профиля
недостаточно для подтверждения активного lease.

lease_id в этой проекции статуса — это публичная ссылка наблюдения
sha256:<digest>, помеченная lease_id_kind=observation_sha256 и
source=native_task_db. Приватный Claim-ID остаётся у клиента lease. Ссылка
наблюдения не даёт прав Claim, Renew или Release.

Обратный отсчёт и сортировка являются необязательным отображением. Они не
изменяют ни lease задачи, ни бюджет ходов, не продлевают время работы и не
запускают никакой работы.
