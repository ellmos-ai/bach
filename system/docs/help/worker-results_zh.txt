Worker 结果与个人验收
=============

原生 Worker 使用 task_manage、action=submit_result 和必填标志
complete=true/false（或在 CLI 完成命令中使用 --complete=true/false）来保存具
体的专业结果。其完成别名同样通向结果提交。仅凭完成确认是不够的。当
complete=true 时，结果作为提交保存，任务租约被释放，完成状态根据已配置的策略
确定（review 或直接完成）。当 complete=false 时，迄今为止的部分状态会被密封
记录在任务描述中，任务作为 pending 保持开放状态返回（例如在拆分为子任务之后）。

显式分配给系统槽位的任务，无论其通用的类别和优先级选择如何，都会被接管。标签
过滤器，尤其是 waiting 或 delegated 等排除标签，仍然具有约束力。分配的槽位
和 required_model 必须与实际配置相符。依赖项、Creator 宽限期和现有任务租约
仍然具有约束力。对于没有显式槽位分配的任务，适用以往的队列和受让人过滤器。

已启用的拾取过滤器要求满足所有已配置的过滤组：类别（category、project 或
categories）、优先级、至少一个正向标签且无排除标签。空组不做限制。在没有启
用过滤器且没有显式槽位分配的情况下，通用队列限制为 assigned_to 为 BACH、
Buddha、Ollama 或自身的 Worker-ID、角色或 sub_mode。已启用的过滤器是显式
的选择配置，而非对他人任务的通用放行。

实时收集的 queue_status 投影会列出候选任务、选择匹配项、接管尝试、来源、时
间，以及按类别、优先级、正向或排除标签和原生接管限制分别统计的排除数量。选择
匹配尚不是已确认的租约。current_activity 在较旧的 GUI 卡片中也会显示主要数
字。经过身份验证的配置获取会将 selection_policy 与可编辑字段分开返回。此显
示不会更改、启动或声明任何内容；其选择值已包含在配置版本中。

对于运行检查，正在运行的 Control 服务的配置和执行证明具有决定性意义。新启动
的 CLI 可能因不同的环境变量而读取另一个槽位配置文件，因此仅凭它本身无法证明
实际正在运行的 Worker 可以选择哪些任务。

在任务详情中，Review 显示已保存的结果文本。用户对其进行检查并使用自己的操作
员密钥接受。验收会绑定确切的结果、其 SHA-256、任务内容版本和状态修订版本。
最新获取可确认实际保存的验收。

操作员仅在规范后端本地配置：
gui.device_auth.create_task_result_operator(name)。该函数创建一个新的设备
凭据；现有的托盘、Worker 和通用设备密钥不会因此获得验收权限。个人密钥会私密
传输给用户并保存在当前浏览器标签页中。忘记会将其从该标签页中移除。它既不属于
仓库，也不属于工单、日志、模型上下文或 SYNC。

GET /api/tasks/{id}/result 读取提交和当前验收。
POST /api/tasks/{id}/result/accept 额外要求 X-BACH-Result-Operator。仅凭
通用设备身份验证不允许此验收。已吊销的操作员设备、被修改的结果、任务内容或状
态修订版本会被拒绝。历史结果会保留以供查阅，但不视为当前已确认的验收。

接力（Staffel）在物理 Worker 结束后会等待此单独验收。在结果来源未确认时，它
保持相同的步骤绑定并等待。只有经过确认的当前验收才允许移交至下一步骤。即使在
等待缺失的来源时，也可以显式停止。
