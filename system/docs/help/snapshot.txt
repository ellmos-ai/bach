BACH SNAPSHOT SYSTEM
====================

STAND: 2026-09-16 (Task #1207 umgesetzt: load = echter Restore)

Session-Snapshots sichern den exakten "State of Mind" einer KI-Session. 
Dies ermöglicht das Laden eines Kontexts in eine neue Instanz oder 
das Fortsetzen nach einem Absturz/Shutdown.

BEFEHLE
-------
  bach --snapshot create [name]   Aktuellen Status sichern (fuellt ALLE Schema-Spalten).
  bach --snapshot list            Verfügbare Snapshots (auto & manuell).
  bach --snapshot load [ID]       ECHTER Restore: Working Memory & Tasks zurueckschreiben.
  bach --snapshot load [ID] display  NUR anzeigen (keine Schreibvorgaenge).
  bach --snapshot delete <ID>     Entfernt alte Snapshots.

RESTORE-SEMANTIK (Stand 2026-09-16, nicht-destruktiv & idempotent):
  - WORKING MEMORY: Im Snapshot gesicherte, aber im Live-System fehlende
    aktive Eintraege werden als neue aktive memory_working-Rows (type='note')
    zurueckgeschrieben. Identische aktive Eintraege werden uebersprungen
    (keine Duplikate).
  - TASKS: Erledigte/geloeschte Tasks aus dem Snapshot werden reaktiviert
    (status='pending'); voellig fehlende Tasks werden als neue pending-Tasks
    mit source='snapshot-restore' angelegt. Bereits offene Tasks = No-Op.
  - current_session wird NICHT ueberschrieben (Sicherheitsabstand).
  - `display` als zweites Argument schaltet auf reinen Anzeigemodus.

KONZEPT: DER STATE-TREE
-----------------------
Ein Snapshot in BACH besteht aus folgenden Komponenten:
1. SESSION-ID: Aktueller Session-Kontext
2. OPEN TASKS: Welche Tasks aktiv/offen waren (bis zu 10)
3. RECENT MEMORY: Letzte Working Memory Einträge (letzte 5)
4. SNAPSHOT-METADATEN: Timestamp, Type (auto/manual), Name

UNTERSCHIED ZU ANDEREN SYSTEMEN
-------------------------------
- MEMORY: Wichtiges Wissen (langfristig).
- LOGS: Was getan wurde (historisch).
- SNAPSHOT: Wo wir gerade stehen (operativ).

AUTOMATIK
---------
Snapshots können automatisch oder manuell erstellt werden.

MANUELL: `bach --snapshot create [name]` → snapshot_type='manual'.
AUTO:    hub/shutdown.py erstellt bei >= 3 erkannten Aenderungen ein Auto-Snapshot
         (Name: auto_YYYYMMDD_HHMMSS).

ACHTUNG: Auto-Snapshots werden ebenfalls mit snapshot_type='manual' gespeichert
(nur der Name enthaelt 'auto_...'; shutdown.py ruft denselben _create-Pfad).
Verifiziert 2026-09-16.

DATENBANK
---------
Tabelle: `session_snapshots` (data/schema/schema.sql, ab Zeile 347)
Felder (SOLL=IST seit 2026-09-16):
  - id, session_id, snapshot_type, name
  - snapshot_data (JSON: session_id, open_tasks, recent_memory, active_files,
    token_usage, created_at)
  - working_memory, open_tasks, active_files (separate JSON-Spalten, gefuellt)
  - token_usage (letzte Gesamt-Zahl aus monitor_tokens, falls vorhanden)
  - context_hash (sha256 der Snapshot-Daten, erste 16 Hex-Zeichen)
  - notes, created_at

IST-ZUSTAND (2026-09-16): Handler hub/snapshot.py _create befuellt ALLE
Schema-Spalten (INSERT mit working_memory, open_tasks, active_files,
token_usage, context_hash, notes). _load bevorzugt die separaten Spalten
und faellt auf snapshot_data zurueck (abwaertskompatibel fuer aeltere
Snapshots ohne Spaltenbefuellung).

BEISPIELE
---------
  bach --snapshot create "Vor Grossumbau"   # Manuelles Backup
  bach --snapshot list                      # Status prüfen
  bach --snapshot load 42                   # Restore: Memory & Tasks zurueckschreiben
  bach --snapshot load 42 display           # Nur anzeigen, nichts veraendern
  bach --snapshot delete 42                 # Snapshot 42 löschen
