WORKER-SCOPE-EVIDENCE — 結果のためのプロジェクトおよびワークツリー証明
=======================================

提出された結果は不変のスコープ証明を受け取ることができます。最初のアダプタは
bach-task/<Task-ID> 上のクリーンな BACH タスクワークツリーの既存登録を使用しま
す。他のプロジェクトでは、実際のリポジトリ/スコープ権限への独自の接続が必要で
す。証明が欠落していても、従来の個人受け入れや修正は妨げられません。

プライベートコントローラは、正規の Result、そのタスクバージョン、世代、フェンス、
および提出リビジョン、ならびにリポジトリ、ブランチ、Head、および Git ツリーを
記録します。解決されたローカルパスは SHA-256 としてのみ保存されます。既存の公開
ソースピンが確認され、その欠落が公に確認された出所として出力されることはありま
せん。プロンプト、応答、プライベートリース ID、および認証情報はこの証明に含ま
れません。

定義された Git スコープには、インデックス、追跡ファイル、および無視されていない
新規ファイルが含まれます。staged/unstaged/untracked の変更、ならびに
assume-unchanged および skip-worktree は正の証明を妨げます。サブモジュールおよ
び設定された Git ファイルフィルタは最初のアダプタでは利用不可のままであり、この
スコープチェックはフィルタプログラムを実行しません。無視されたファイルは明示的
にこの Git スコープ外にあります。クリーンなコミットは依頼の技術的な履行を証明し
ません。

Git と SQLite には共通のトランザクションがありません。Git と現在のロックは
SQLite 書き込みロックの外で記録され、書き込みロック内で正規の結果バインディング
が再確認されます。証明は観測された状態を記述します。2 回のクエリ間での恒久的な
排他性や不変性を証明するものではありません。

read_result() は SQLite 読み取りスナップショット内で保存された証明と履歴のみを
確認します。result.scope.availability=recorded は、過去の証明が有効であり、現在
のワークツリーはまだ再確認されていないことを意味します。result.result_revision
は null のままです。ローカル SDK 取得および API GET はその後、Git/登録/ロックを
再確認します。API はイベントループ外で接続を閉じた後にこのチェックを実行します。
呼び出し元によってすでに開かれた SQLite スナップショットは SDK によって閉じられ
ず、そのスナップショット内では追加の Git 射影は行われません。

変更なしでスコープが確認された場合にのみ availability=available が表示されます。
変更された Head、ダーティなツリー、または利用不可の Git/ロックサービスは
unavailable を返し、完全な結果リビジョンを返しません。既存の結果証明がより新し
いワークツリー状態によって上書きされることはありません。新しい提出には新しい結
果世代が必要です。

完全な result_revision は、提出リビジョン、実際に確認された実行リビジョン、お
よびスコープ証明ダイジェスト/履歴イベントをバインドします。実行証明が欠落してい
る場合は null のままです。CLI 実行では Submit 後にすでにスコープが存在する場合が
ありますが、それでもリビジョンは実際のモデルリターンと確認済み実行リンクの後に
のみ生成されます。失われた Submit-ACK は、自身のプライベートな期待される提出の
正確な正規リードバックによってのみ再構築できます。

プライベートローカル記録は TaskLeaseClient._capture_task_scope および
WorkerLeaseBinding.capture_confirmed_scope を使用します。ディスパッチャは確認
済みタスク操作の後にバインディングロック外でこれらを呼び出します。直接のローカ
ル呼び出し元はこれらを明示的に呼び出すことができ、result_state は必要に応じて
まず実際の Submit を再構築します。同一結果 ID の繰り返しの成功記録はバインディ
ング内で回避されます。現在の公開取得は引き続きそのスコープを再確認します。リモー
トクライアントは自己申告エンドポイントもローカル DB フォールバックも受け取りま
せん。

有効なリビジョンはレビュー権限も Done も付与しません。著者およびレビュアーのアイ
デンティティ、モデルレベル、独立性、技術的タスク契約、ユーザー義務、および
GitHub ゲートは、それぞれ独自の認可された証明を提供する必要があります。後の承認
は、その時点の現在の状態を再確認する必要があります。
